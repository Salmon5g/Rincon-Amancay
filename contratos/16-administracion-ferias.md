# Administración de ferias

## Rutas y documentos

La colección `ferias/{feriaId}` contiene `nombre`, `descripcion`, `organizador`, `direccion`, `fechaInicio`, `fechaFin`, `imagenUrl`, `estado`, `creadoEn` y `actualizadoEn`. Puede incluir el par opcional `latitud`/`longitud`. `descripcion` e `imagenUrl` son obligatorias al crear y editar: la imagen debe ser una URL HTTPS pública, normalmente la devuelta por la carga de imagen de feria. Las fechas se guardan como Timestamp; la API recibe ISO 8601 con zona horaria. El UID del actor queda en la auditoría, no en el documento con lectura pública.

Estados de feria: `borrador`, `publicada`, `cancelada`. Crear produce un borrador. Publicar requiere que el inicio aún no ocurra. Las ferias canceladas quedan como historial terminal; no se borran. Una feria publicada se puede editar antes de su inicio.

`ferias/{feriaId}/participantes/{tipo}_{entidadId}` contiene `tipo` (`emprendedora` o `asociacion`), `entidadId`, `nombre`, `estado`, `creadoPor`, `creadoEn` y `actualizadoEn`. Para emprendedoras puede incluir `nombreTienda`. `asistencia` solo se usa para participantes confirmados o agregados directamente. Estados de participación: `invitada`, `confirmada`, `rechazada`, `agregada_admin` y `retirada`.

La API construye los nombres desde los registros vigentes; el cliente no puede proporcionar el UID del actor ni sustituir el nombre de una persona. Solo se invitan cuentas emprendedoras activas con perfil y tienda coherentes o asociaciones activas. No se guardan correos personales en la participación.

## Operaciones

- `listarFeriasAdmin`, `crearFeria`, `editarFeria`, `cambiarEstadoFeria`.
- `leerParticipantesFeria`, `invitarParticipanteFeria`, `cancelarInvitacionFeria`, `agregarParticipanteFeria`, `retirarParticipanteFeria`, `registrarAsistenciaFeria`.
- `responderInvitacionFeria` queda disponible para clientes emprendedora autenticados; solo la persona destinataria puede confirmar o rechazar su invitación.
- `listarInvitacionesFeria` devuelve a la emprendedora autenticada sus participaciones en ferias en borrador o publicadas, incluidas invitaciones, respuestas y registros directos de administración (`agregada_admin`). No lista ferias canceladas ni participantes de otras cuentas.
- `enviarRecordatorioFeria` envía una notificación push a la cuenta emprendedora con invitación pendiente. Se entrega por el tema `amancay-invitacion-{uid}` y contiene el UID destinatario, el ID y nombre de la feria y el ID estable de la operación. Al pulsarla, la app abre `Invitaciones a ferias` para responder la invitación. La API registra el mensaje como aceptado por Firebase Cloud Messaging, lo que no garantiza que el dispositivo lo haya recibido. El control de recordatorios limita los reenvíos a uno cada 24 horas; un reintento de la misma operación conserva su identificador. Las asociaciones no tienen actualmente una bandeja de invitaciones en la app, por lo que no se ofrece este recordatorio push para sus filas.
- `enviarAvisoConfirmadasFeria` envía manualmente un aviso push W10 a una emprendedora con participación confirmada en una feria publicada que aún no comienza. En Administración > Ferias > Participantes, «Avisar a confirmadas» abre un selector de destinatarias con confirmación de envío; no añade botones por fila. El aviso incluye nombre, fecha, dirección y organización de la feria; al tocarlo, la app abre Invitaciones a ferias, selecciona el día correspondiente en el calendario y destaca la feria. El servidor valida la cuenta activa, conserva idempotencia y limita avisos repetidos a uno por destinataria cada 24 horas. Firebase confirma aceptación del mensaje, no la entrega al dispositivo. No se envía por correo ni a asociaciones, cuya app todavía no cuenta con una bandeja compatible.

La imagen de la feria se carga con `POST /api/v1/ferias/imagen`. Requiere una sesión administradora activa, un `X-Archivo-Id` UUID para reintentos idempotentes y un cuerpo binario JPEG, PNG o WebP de hasta 5 MiB. La API guarda el original privado, publica una versión WebP en el almacenamiento y responde `{ datos: { ruta } }` con la URL HTTPS pública que luego se envía como `imagenUrl` en `crearFeria` o `editarFeria`.

Las modificaciones de administración requieren rol activo, versión vigente y `operacionId` estable para reintentos. Se guardan recibos y auditoría en las colecciones administrativas compartidas. `cancelarInvitacionFeria` solo acepta una invitación pendiente, elimina el documento de participación para que la entidad vuelva a estar disponible y conserva el evento en auditoría. `retirarParticipanteFeria` solo acepta participantes confirmados o agregados directamente y conserva su registro con estado `retirada`. La asistencia solo se registra durante el intervalo `[fechaInicio, fechaFin)`, únicamente para participantes confirmados o agregados por administración en ferias publicadas. La interfaz deshabilita los botones fuera de ese horario y la API valida el intervalo en cada solicitud. Una invitación pendiente no tiene estado de asistencia; al aceptar, queda como `pendiente`. Si la feria termina sin registro, se muestra `Sin asistencia registrada` y no se interpreta como `no_asistio`.

## Lectura, límites y pendientes

Las reglas permiten lectura pública de ferias publicadas; los documentos de participantes son visibles solo a administración, porque incluyen identificadores de cuentas. El comprador Android obtiene las ferias publicadas mediante GET /api/v1/feriasPublicas y, sin token, usa GET /api/v1/feriasPublicas/{feriaId} para participantes confirmadas, nombres públicos y una muestra de hasta tres productos publicados por tienda. La política pública de navegación se lee mediante GET /api/v1/configuracionPublica/navegacion; Android usa la API como respaldo cuando Firestore no responde. Para asociaciones usa hasta tres tiendas de su proyección pública. La respuesta no contiene UID, precios ni datos administrativos; la ruta tiene límite de 30 lecturas por minuto por IP. El cliente no consulta directamente la subcolección privada. Las escrituras directas permanecen denegadas. La consulta actual del comprador filtra `estado == "publicada"` y ordena por `fechaInicio` en el cliente; no usa `orderBy`. Firestore resuelve el filtro con su índice automático de campo único. El índice compuesto `ferias(estado ASC, fechaInicio ASC)` sigue declarado en `firebase/firestore.indexes.json` para una consulta futura que ordene en Firestore, pero no es necesario para la consulta actual.

La ficha web en modo `real-lectura` no puede consultar la subcolección privada de participantes. Para que W12 y W13 funcionen sin API, la administración mantiene en el documento público `ferias/{feriaId}` el campo `participantesPublicos`: una lista sin UID con `tipo`, `nombre`, `tiendaIds` y, solo para asociaciones, `asociacionId`. Se recalcula al publicar una feria, al confirmar o agregar una participación, al retirarla y al cancelar una invitación. Para datos existentes, `npm.cmd --prefix backend run ferias:actualizar-participantes-publicos -- --dry-run rincon-amancay` simula la actualización; revisar el resumen antes de ejecutar con `--aplicar`. La web resuelve la muestra de catálogo consultando únicamente las proyecciones públicas de tienda y sus productos con `estadoPublicacion == "publicado"`.

La invitación inicial a una emprendedora también se notifica por push. Registrar una invitación a una asociación conserva el registro de Firebase, pero no genera una notificación en la app porque la bandeja emprendedora aún no contempla respuestas de asociaciones. La imagen se sube al almacenamiento (Supabase Storage) y el documento guarda su URL pública; el formulario también permite marcar la ubicación en un mapa o buscarla por dirección. La página pública de ferias del comprador web está disponible en `/comprador/ferias`.
